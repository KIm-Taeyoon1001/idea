# IDEA-006 — StackRetire
> 프로젝트 단위 멀티-PaaS 클라우드 자원 종료·인계 관리 SaaS  
> 상태: **초기 사업 가설 — 고객 인터뷰 및 유료 검증 전**  
> 작성일: 2026-11-12  
> 제품명은 작업명이며 상표·도메인 사용 가능 여부는 별도 확인이 필요하다.

## 1. 한 문장 요약

GitHub 저장소와 클라우드/PaaS 계정을 연결해 하나의 앱 프로젝트에 속한 배포·DB·스토리지·도메인·작업·비밀정보 관련 자원을 찾아 연결하고, 프로젝트 종료 시 **백업 → 소유권 이전 → 접근권한 정리 → 보존기간 확인 → 자원 종료** 순서의 검토 가능한 종료 계획과 증빙 보고서를 만드는 도구다.

StackRetire는 클라우드 자원을 임의로 삭제하는 자동 정리 봇이 아니다. 첫 MVP는 읽기 전용으로 자원을 조사하고, 사람이 소유권과 종료 여부를 확인한 뒤 실행할 체크리스트를 만든다.

## 2. 불편함 발견

개발자는 프로젝트를 GitHub에서 archive하거나 저장소를 삭제해도 실제 운영 자원이 자동으로 정리되지 않는 경우가 있다.

프로젝트 하나가 다음과 같이 여러 공급자에 분산될 수 있다.

- 코드 저장소와 CI/CD
- 웹 배포 프로젝트와 preview deployment
- 데이터베이스, 인증, 파일 스토리지
- 서버리스 함수, 예약 작업, 큐
- DNS, 도메인, TLS 인증서
- 이메일 발송·웹훅·OAuth 연동
- 모니터링, 분석, 로그 보관
- API 토큰과 서비스 계정

프로젝트 종료를 담당하는 사람은 각 공급자 대시보드를 하나씩 열어 자원을 찾아야 한다. 빠뜨리면 불필요한 비용이나 사용하지 않는 접근 권한이 남고, 반대로 성급하게 삭제하면 고객 데이터·도메인·공유 인프라가 사라질 수 있다.

### 근본 원인

1. **프로젝트 ID가 공급자마다 다르다.** GitHub 저장소명, 배포 프로젝트명, DB 프로젝트 ID, DNS zone은 서로 자동 연결되지 않는다.
2. **자원 소유권이 불명확하다.** 한 DB나 도메인을 여러 앱이 공유할 수 있고, 이름만으로 실제 의존성을 확정하기 어렵다.
3. **종료 절차가 분산되어 있다.** 백업, 고객 인계, 도메인 이전, 키 폐기, 결제 종료가 서로 다른 대시보드와 문서에 흩어져 있다.
4. **삭제 위험이 크다.** 공급자별 삭제 범위와 복구 가능 기간이 다르며, 일부 삭제는 되돌릴 수 없다.

Supabase는 프로젝트 삭제 시 데이터베이스, 스토리지, 백업, 인증 데이터와 설정 등이 영구 제거되고 복구할 수 없다고 안내한다. Vercel도 프로젝트 삭제 시 배포, 도메인, 환경변수와 설정이 함께 삭제된다고 설명한다. 따라서 단순히 '오래된 자원'을 찾아 지우는 방식으로는 안전한 프로젝트 종료를 보장하기 어렵다.  
출처: [Supabase — Deleting Your Project](https://supabase.com/docs/guides/platform/delete-project), [Vercel — Managing Projects](https://vercel.com/docs/projects/managing-projects)

### 경쟁 분석 결론

클라우드 인벤토리, 고아 자원 탐지, 임시 환경 정리, 단일 공급자 삭제 도구는 이미 존재한다. 따라서 “여러 클라우드 자원을 한곳에서 보여준다”만으로는 차별화가 성립하지 않는다.

StackRetire가 검증해야 할 틈새는 **GitHub 저장소를 출발점으로 여러 PaaS 자원을 하나의 고객 프로젝트에 귀속시키고, 안전한 종료·인계 절차를 증빙하는 업무**다. 경쟁 제품이 이미 이 전체 흐름을 제공한다면 아이디어를 폐기하거나 더 좁은 고객군으로 재설계한다.

## 4. 차별화 가설

1. **코드 저장소에서 시작:** 배포 설정 파일과 프로젝트 메타데이터를 읽어 자원 후보를 찾는다.
2. **프로젝트 중심 연결:** 공급자별 계정·자원 목록을 프로젝트별 관계도로 묶고, 매칭 근거와 신뢰도를 표시한다.
3. **종료 전 안전 확인:** 공유 자원 여부, 데이터 백업, 도메인 연결, 고객 소유권, 보존 의무, 접근권한을 체크한다.
4. **사람이 승인:** 소유자·고객 담당자가 각 자원의 유지/이전/일시중지/종료 여부를 확인한다.
5. **인계 증빙:** 누가 무엇을 확인했고 어떤 자원을 유지·이전·종료하기로 했는지 PDF/JSON 보고서로 남긴다.

이 차별점은 현재 검증된 경쟁 우위가 아니라 인터뷰에서 검증할 가설이다.

## 5. 제품 설명 및 사용자 흐름

### 핵심 사용자 흐름

1. 사용자가 GitHub 저장소 하나를 연결한다.
2. StackRetire가 공개 가능한 배포 설정과 인프라 선언 파일을 읽어 자원 후보를 추출한다.
3. 사용자가 Cloudflare, Vercel, Supabase 등 지원 공급자를 **읽기 전용 권한**으로 연결한다.
4. 공급자 API에서 확인한 자원과 저장소의 후보를 매칭한다. 이름·ID·환경변수 이름·배포 메타데이터 등 매칭 근거를 보여주고 불확실한 항목은 '미확인'으로 남긴다.
5. 사용자가 각 자원의 소유자, 공유 여부, 운영/개발 여부를 확인한다.
6. 시스템이 자원별로 다음 상태를 제안한다.
   - 유지
   - 새 소유자에게 이전
   - 데이터 백업 후 일시중지
   - 보존기간 확인 후 종료 검토
   - 소유자 확인 필요
7. 담당자가 검토를 완료하면 프로젝트 종료 체크리스트와 인계 보고서를 내보낸다.

### MVP 기능

- GitHub 저장소 연결 및 설정 파일 정적 분석
- 첫 지원 후보: Cloudflare, Vercel, Supabase
- 공급자별 읽기 전용 자원 인벤토리
- 자원-프로젝트 매칭 근거와 신뢰도
- 공유/운영/테스트 자원 확인
- 백업·도메인·접근권한·고객 승인 체크리스트
- 사람의 확인 내역과 최종 종료 보고서(PDF/JSON)

### MVP에서 하지 않을 것

- 자원을 자동 삭제하거나 공급자 계정의 쓰기 권한을 요구하지 않는다.
- 데이터베이스 백업·복원을 자동으로 수행한다고 주장하지 않는다.
- 자원 이름만 보고 소유권이나 공유 여부를 확정하지 않는다.
- 법적 보존 의무나 계약상 종료 의무를 법률 자문처럼 판정하지 않는다.

## 6. 타깃 고객

### 1차 타깃

- 여러 고객 사이트를 운영하는 소규모 웹·앱 개발 에이전시
- 프로젝트를 자주 만들고 종료하는 프리랜서 개발팀
- 실험·프로토타입을 다수 운영하는 소규모 SaaS 팀

### 2차 타깃

- 해커톤·액셀러레이터 운영팀
- 외부 개발사에 프로젝트를 맡겼다가 인수하는 중소기업 IT 담당자

첫 시장은 대기업 클라우드 인프라 조직이 아니다. 대기업은 기존 CMDB, FinOps, 보안·변경관리 체계를 이미 갖췄을 수 있고 구매 절차도 길다.

## 7. 고객이 사용해야 할 이유

- 프로젝트 종료 때 공급자 대시보드를 여러 번 오가며 자원을 찾는 시간을 줄일 수 있다.
- 남은 자원과 소유자를 확인해 불필요한 비용·접근권한을 발견할 수 있다.
- 삭제 전에 데이터·도메인·공유 의존성을 확인해 실수 위험을 낮출 수 있다.
- 고객에게 무엇을 이전하고 무엇을 종료했는지 명확한 인계 기록을 제공할 수 있다.

단, 실제로 얼마나 많은 자원이 남고 고객이 얼마를 지불할지는 아직 확인되지 않았다.

## 8. 수익 모델 및 가격 가설

| 플랜 가설 | 가격 가설 | 제공 범위 |
|---|---:|---|
| Solo | 월 $9 | 연결 프로젝트 3개, 종료 보고서 기본 제공 |
| Studio | 월 $39 | 프로젝트 20개, 팀 검토, 고객 인계 보고서 |
| Agency | 월 $99 | 프로젝트 100개, 역할별 승인, 고객별 이력 |
| One-off | 프로젝트당 $19 | 단일 프로젝트 종료 점검 보고서 |

- 가격은 시장에서 확인한 실제 지불 의사가 아니라 초기 실험용 가설이다.
- 고객이 종료 시점에만 제품을 쓰는 경우 구독보다 프로젝트당 결제가 더 적합할 수 있다.
- 월간 반복 매출을 만들려면 종료뿐 아니라 프로젝트 생성·운영·인계까지 확대해야 하지만, MVP에서 범위를 넓히지 않는다.

## 9. MVP 개발 계획

### 1단계 — 문제 검증 (1~2주)

- 에이전시/프리랜서/인디 개발자 12~15명 인터뷰
- 최근 종료한 프로젝트 5개의 자원 목록을 고객 동의하에 익명으로 확인
- 실제로 남아 있던 자원, 월 비용, 정리 소요시간, 사고 경험을 기록
- 공급자 연결 없이 수동 체크리스트로 먼저 문제를 검증

### 2단계 — 수동형 MVP (2~3주)

- GitHub 저장소에서 배포 설정 파일을 읽어 자원 후보 추출
- 사용자가 공급자 자원 목록 CSV를 업로드
- 프로젝트별 자원 매핑과 검토 상태 표시
- 종료 체크리스트 및 PDF/JSON 보고서 출력

### 3단계 — 읽기 전용 연동 (3~5주)

- 실제 인터뷰에서 사용 빈도가 확인된 공급자 2~3개만 연동
- 최소 권한 OAuth/API 토큰 범위 설계
- 매칭 정확도와 미확인 자원 비율 측정
- 쓰기/삭제 권한 없이 파일럿 운영

## 10. 고객 확보 전략

1. 소규모 웹 에이전시와 프리랜서 개발자에게 최근 종료한 프로젝트가 있었는지 인터뷰한다.
2. '프로젝트 종료 체크리스트' 무료 템플릿을 배포해 실제 수요를 확인한다.
3. 동의한 팀의 프로젝트 하나를 수동으로 조사해 종료 보고서를 만들어 준다.
4. 보고서가 실제 업무 시간을 줄였고 유료 지불 의사가 확인된 팀에만 파일럿을 제안한다.
5. 에이전시가 고객에게 제공하는 표준 인계 문서로 채택될 수 있는지 확인한다.

광고를 먼저 집행하지 않는다. 초기에는 직접 인터뷰와 수동 파일럿으로 문제의 빈도와 지불 의사를 확인한다.

| 보고서 파일 저장 | 소량 저장소 | 월 $0~5 |
| 이메일/알림 | 무료 한도 | 월 $0~5 |
| 총계 | 초기 소규모 파일럿 가정 | 월 $0~30 |

위 수치는 실제 공급자 견적이나 확정 요금이 아니라 소규모 파일럿을 위한 예산 가설이다. 공급자 API 사용량, 저장 기간, 사용자 수, 환율, 유료 플랜 요구사항에 따라 달라진다. 개발자의 시간과 법률·보안 검토 비용은 포함하지 않았다.

## 12. 확장성

- 추가 PaaS·서버리스·데이터베이스 공급자 커넥터
- 고객 프로젝트별 소유권·인계 승인 기록
- 정기 인벤토리와 프로젝트 종료 후보 탐지
- 고객사에 전달하는 인계 보고서 브랜딩
- 공급자별 자원 매핑 규칙을 플러그인 형태로 확장

장기적으로는 개발 에이전시의 프로젝트 수명주기 관리 도구가 될 수 있지만, 실제 확장은 초기 고객의 반복 사용이 확인된 이후에만 검토한다.

## 13. 법적·운영상 리스크와 대응

| 리스크 | 대응 |
|---|---|
| 공유 DB·도메인·스토리지를 잘못 종료 | 자원 매칭은 후보로만 표시하고 소유자 확인을 필수화 |
| 백업 누락 및 복구 불가 | 공급자별 백업 상태를 확인하고 별도 백업 완료를 증빙하기 전 종료 승인 금지 |
| API 토큰 유출 | 읽기 전용 최소 권한, 암호화 저장, 연결 해제·토큰 폐기 지원 |
| 고객 데이터·개인정보 보존 의무 | 보존기간은 고객이 지정하고, 법률 판단은 고객·전문가에게 맡김 |
| 공급자 API 변경·요금제 차이 | 커넥터별 지원 범위와 마지막 확인 시각을 명시 |
| 잘못된 자동 매칭 | 신뢰도·근거 표시, 미확인 상태 유지, 삭제 자동화 금지 |
| 일회성 사용으로 낮은 반복 매출 | 프로젝트당 결제와 에이전시 구독을 함께 검증 |
| 보안 사고 및 책임 범위 | 제품은 조사·체크리스트·기록 도구로 한정하고 파괴적 작업을 실행하지 않음 |

## 14. 시장 검증 지표

첫 30일 동안 다음 기준을 검증한다.

- 인터뷰 12~15건 완료
- 최근 12개월 내 종료한 프로젝트 5건의 실제 자원 목록 확인
- 인터뷰 대상 중 8명 이상이 종료 과정에서 누락 자원·정리 시간·인계 문제를 겪었다고 확인
- 수동 인벤토리에서 자원 매칭 정확도 90% 이상을 달성할 수 있는지 측정
- 유료 파일럿 또는 프로젝트당 보고서에 실제 결제 의사를 보이는 고객 3곳 확보

위 기준은 성공을 보장하는 수치가 아니라 계속 개발할지 판단하기 위한 사전 가설이다. 고객 인터뷰에서 문제가 드물거나 기존 도구로 충분히 해결된다면 개발을 중단한다.

## 16. 최종 판단

**판단: 좁은 범위의 문제 검증을 진행할 가치가 있는 초기 가설.**

멀티클라우드 자원 인벤토리와 고아 자원 정리 도구가 이미 존재하므로 범용 클라우드 정리 서비스로 진입하면 경쟁력이 약하다. GitHub 저장소를 기준으로 서버리스/PaaS 자원을 프로젝트에 귀속시키고, 데이터 보존·고객 인계·종료 승인 기록을 함께 제공하는 범위에서만 차별화 가능성을 검증한다.

현재 고객 인터뷰, 실제 비용 절감, 유료 전환, 자원 매칭 정확도는 검증되지 않았다. 이 수치를 확보하기 전에는 시장성이나 독창성을 확정하지 않는다.
